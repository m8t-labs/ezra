# Prereqs — macOS

> 🤖 **Agent runbook (component step).** Your coding agent opens this from the install flow and runs it top-to-bottom. Idempotent — safe to re-run.
>
> Prereqs the agent installs and verifies before continuing with `install.md`. For Windows, see `install/prereqs-windows.md`.

---

## Read this first (you, the agent reading this file)

**Scope.** Your only job while following this file is: install the prerequisites, install Azure CLI, and authenticate the user against Azure. **Do not modify, create, or delete any files unrelated to this scope.** Do not "improve" the user's shell config, install unrelated tooling, or touch anything in their workspace. If a step fails, report the failure and ask — don't paper over it by editing files outside this scope.

**Interaction style.** Run commands without asking when they are non-destructive and the next step is unambiguous. Pause and ask the user only when:

- A browser-based or interactive flow needs them (`az login`, GUI prompts).
- Multiple valid choices exist and the right one is non-obvious (e.g. multiple Azure subscriptions / tenants).
- A command requires elevated privileges (`sudo`) that haven't been pre-authorized.
- Something fails in a way that needs human judgment.

**Verify the deprecation status before installing — important.**

Microsoft is migrating macOS Azure CLI installs from the Homebrew **formula** (`brew install azure-cli`) to a Homebrew **Cask** (`brew install --cask azure-cli`). The formula method below is **on a deprecation path with no announced timeline.** Before running the install, fetch the official install doc and decide which method to use:

- **Authoritative source:** <https://learn.microsoft.com/en-us/cli/azure/install-azure-cli-macos>
- **What to look for:** the page shows the currently recommended Homebrew method. The page text and code blocks describe whether the migration is still "in preview" (use the formula) or "generally available" / GA (use the Cask).
- **Decision:**
  - If the formula path (`brew install azure-cli`) is still listed as supported and the Cask is described as preview → **use the formula instructions in this file as written.**
  - If the Cask path (`brew install --cask azure-cli`) is now GA from the official Cask repo → **swap the install command for `brew install --cask azure-cli`** and continue with the rest of this file unchanged. Note the swap to the user.
  - If the page describes a different method entirely → follow the official doc and report what changed back to the user.
- **After resolving the install:** if you found the file out of date, mention it to the user so they can update this markdown for future runs. Do not edit this file yourself unless explicitly asked.

This deprecation check is cheap (one `WebFetch` or equivalent) and it's the difference between this file aging gracefully and breaking the moment Microsoft flips the GA switch.

## Goal

End state: `az --version` works, `az account show` returns an active subscription, and the active tenant matches the one the user expects to use with Microsoft Foundry. After that the m8t install can proceed.

## Step 0 — Pre-check

If `az` is already installed, refresh it to the latest before proceeding.

```bash
az --version
```

- Command not found → continue with prereq install (Step 1).
- Command exists → run `az upgrade --yes` to ensure the user has the latest version. This is a non-interactive upgrade; `--yes` answers the "upgrade extensions too?" prompts automatically. If `az upgrade` fails (e.g., permission error, package-manager conflict), surface the verbatim error but **do not block** — the existing `az` will still work. Then jump to **Step 4 — Login** (and skip `az login` if `az account show` already returns a valid subscription).

```bash
az upgrade --yes
```

## Step 1 — Xcode Command Line Tools (Homebrew prereq)

Required for Homebrew. Triggered automatically by the Homebrew installer on first run, but explicit is faster:

```bash
xcode-select -p >/dev/null 2>&1 || xcode-select --install
```

If `xcode-select --install` runs, a GUI dialog appears asking the user to confirm the install. **This is one of the moments to pause and tell the user**: "macOS will pop up a dialog to install the Xcode Command Line Tools. Click Install and let me know when it finishes (typically 2-5 minutes)."

Verify:

```bash
xcode-select -p   # should print a path under /Library/Developer/...
```

## Step 2 — Homebrew

If Homebrew is already installed (`brew --version` works), skip this step.

```bash
which brew >/dev/null 2>&1 || /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

The installer is interactive in some scenarios (it confirms the install path and asks for the user's macOS password for `sudo`). **Pause and tell the user** before running it: "Installing Homebrew. It will prompt for your macOS password to use sudo — please type it when prompted."

After install on Apple Silicon, Homebrew is at `/opt/homebrew/bin/brew` and may not be on PATH for the current shell. Either run the post-install hint Homebrew prints, or in this session source it directly:

```bash
eval "$(/opt/homebrew/bin/brew shellenv)"
```

Verify:

```bash
brew --version
```

## Step 3 — Azure CLI

> **Confirm the deprecation status first** (see "Read this first" at top). Pick the install command based on the official doc, not from memory.

**Current method (formula — works today, deprecation-pending):**

```bash
brew update && brew install azure-cli
```

**If the official doc says the Cask is now GA, use this instead (or use the formulae defined in the updated instructions):**

```bash
brew update && brew install --cask azure-cli
```

This pulls in transitive dependencies automatically (Python 3.13, OpenSSL, libsodium, libyaml, mpdecimal, sqlite). Total disk footprint is around 460MB — flag this to the user only if you have reason to believe their disk is constrained.

Verify:

```bash
az --version
```

Expected: a multi-line block starting `azure-cli 2.x.x`. If the command isn't found right after install, the shell's PATH cache is stale — open a fresh shell, or `hash -r` (zsh/bash) and retry.

## Step 3b — Node.js (≥ 20)

The **local** install needs Node ≥ 20 — not only the cloud surface: `install/m8t.md` writes a render-provenance sidecar with a Node script, and the `m8t` CLI (which `m8t architect-check` invokes at the end of `install/m8t.md`, and which manages your deployment) requires Node 20+.

```bash
which node >/dev/null 2>&1 || brew install node
node --version   # need >= 20
```

If `node` was just installed and isn't found, open a fresh shell or run `hash -r`.

## Step 4 — Login

```bash
az login
```

This opens the user's browser. **Pause and tell the user**: "A browser window will open for Azure sign-in. Complete the sign-in with the account that has access to the Foundry project, then come back."

After login, confirm a subscription is active:

```bash
az account show --query '{name:name, id:id, tenant:tenantId, user:user.name}' -o json
```

If the user has multiple subscriptions and the wrong one is default, list and switch:

```bash
az account list --query '[].{name:name, id:id, isDefault:isDefault}' -o table
az account set --subscription <id-or-name>
```

When multiple subscriptions are visible, **ask the user which one to use** — don't pick for them.

### Tenant / multi-tenant note

The Foundry MCP fallback chain warns that a tenant mismatch between the MCP token and the resource tenant can cause `agent_update` to fail. If `az login` defaults to a different tenant than the one hosting the Foundry project the user wants to use:

```bash
az login --tenant <tenant-id-or-domain>
```

Ask the user for the tenant ID or domain only if the current tenant clearly mismatches their stated Foundry project; don't ask preemptively.

## Step 5 — "Ready" gate

All of the following must be true before the m8t install can proceed:

- [ ] `az --version` returns a version.
- [ ] `az account show` returns a subscription (not an error).
- [ ] The active subscription / tenant matches what the user said they want to use with Microsoft Foundry.
- [ ] `node --version` returns ≥ 20 (the local install's sidecar + the `m8t` CLI need it).

If any check fails, report which one and stop. Do not attempt to fix it by editing user config files.

A model deployment (e.g. `gpt-4.1-mini`) inside the target Foundry project is also required for the spin-up skill to work end-to-end — but that's the m8t install snippet's responsibility, not this file's.

## Additional prerequisites for the cloud surface

These are only needed if you'll **deploy** the platform (see `deploy.md`), not for the local install:

- **Node ≥ 20** — already installed in the base prereqs (Step 3b above); `m8t deploy` and the hosted-image build need it too.
- **Docker** (with `buildx`) — to build and push the hosted coding-agent image.
- We do **not** use `azd` — the deploy runs via `m8t deploy` (the `m8t` CLI) plus the `az` CLI.
